# Revised plan: conversational companion and task manager

**Status:** Proposed for review. Planning only; implementation requires explicit approval.  
**Source:** [initial-plan1](initial-plan1), the populated original document; `initial-plan.md` is empty. Related findings and justifications: [architecture-review.md](architecture-review.md).  
**Terminology:** “Preserve” means an existing decision recommended for retention, not that the user has approved it. “Change” is proposed. “Open” requires an explicit decision or evidence.

## 1. Product outcome and scope

The product is a conversational companion that helps an individual talk through their day and, with their permission, turn actual commitments into a trustworthy task list. It responds to feelings and context without forcing a task. Text and, later, batch voice feed the same turn pipeline. The user can correct the transcript, discuss a proposal, inspect changes and confirm what gets saved. AI never directly mutates a task.

**Preserve:** Egyptian Arabic and code-switching as first-class test cases; conversational responses in the user's language; user-editable transcript; explicit review before task changes; task data independent of conversation deletion; a deterministic date resolver; bounded current-session context; private beta; no long-term memory, autonomous tools, streaming speech, reminders, calendar sync, recurring tasks or vector database in the initial MVP.

**Proposed MVP:**

- A responsive, accessible conversation screen supporting typed turns and a single batch voice capture path; transcript shown and editable before or after analysis.
- A helpful companion reply, including a useful response when there are no tasks. At most one clarification question per turn; the user may decline to organize.
- A tray of clear proposed creates and selected task changes, displaying title, date, exact evidence, uncertainty and target; users can edit, reject or explicitly confirm. All saved-task claims are based on committed results.
- A simple task list with manual create, edit, complete, reopen, reschedule and delete, plus a date or unscheduled view. Ambiguous references ask rather than guess. Bulk actions are optional until justified by testing.
- Minimum necessary authentication, per-user authorization, secure sessions, private-beta controls, transcript retention/deletion, account deletion, and truthful data handling disclosures before real users. Decide export format and beta launch requirement during the privacy design; do not imply deletion of a user's downloaded export.
- A frozen, human-labeled evaluation suite and deterministic tests; measured cost, errors and latency without logging transcript text.

**Defer:** inference-based workload bars, auto-prioritization, auto-apply, learned preferences, multiple provider fallback, full PWA/offline features, themes, speech streaming, TTS, advanced task hierarchy, automatic task splitting by arbitrary counts, and platform-specific visual polish. If a capability is needed to meet a validated user journey, bring it back with an explicit decision. Text-only Milestone 0 is a feasibility gate, not a redefinition of the eventual voice-first product.

## 3. Proposed architecture and operational flow

Start with a modular monolith: a client, a single API/application process, relational storage, one model provider, and later one speech provider. Use clear modules for conversation, analysis, task lifecycle and privacy; avoid services, queues and generic provider frameworks until needed. Use a clock abstraction only where it improves deterministic tests. Structured logs contain IDs, outcome codes and timing, never raw content. A durable scheduled cleanup mechanism must run even when the application has no traffic; choose the mechanism with the host. Maintain backups and test restore. Details remain subject to D3 and D7.

1. **Capture.** A typed message or an explicitly initiated recording becomes a user-visible transcript. If audio is buffered locally for recovery, disclose it; delete it after confirmed transcript persistence or explicit discard, and expire it under D7. Offline failure must not be presented as saved.
2. **Anchor and analyze.** Persist an immutable user-message revision and its send-time instant and IANA timezone. Gather a bounded, user-owned snapshot of relevant existing tasks and pending proposals, with short aliases and version tokens. If the relevant target is outside that snapshot, ask or perform an authorized targeted lookup; never guess from an incomplete list. Treat all user text as untrusted data. Obtain one schema-validated model response.
3. **Validate and propose.** Verify exact evidence in the current revision, alias/type/owner, intent, lifecycle, dates and editable field bounds. Use similarity only to identify possible duplicates. Keep uncertain operations visible as unchecked suggestions or ask; do not silently create, discard or change a task. Persist an immutable analysis run and pending proposals. The reply describes suggestions, never completed writes.
4. **Review and apply.** Show exact date and a before/after diff for changes. User edits or selects proposals. The server revalidates revisions, ownership and target versions, applies the selected set atomically, and returns only committed outcomes. An acknowledgement is composed from those outcomes. If any item conflicts, nothing in that request is committed and the client can refresh and retry after review.
5. **Correct.** A transcript edit creates a new immutable revision. Old pending proposals are superseded atomically. Applied effects remain, linked by minimal provenance; compare corrected meaning to the prior applied result and the current task version. Offer an explicit update/cancel proposal when a target is unambiguous, otherwise ask. Do not silently revert, duplicate, or overwrite a later manual edit. An analysis failure leaves the edited revision saved with a visible retry state and no active old proposals.

**Conversation behavior:** Pure venting yields an appropriate short response and zero task operations. The companion does not present itself as a therapist, make unsupported factual claims, or push productivity when the user declines. Use only the bounded current session and explicitly saved task data; no inferred emotional memory. Human review assesses warmth, relevance, respect for refusal and factual accuracy in Arabic and mixed language.

## 4. Contract and domain model to finalize before implementation

### Analysis output

Define a versioned strict model-output schema separately from the public API schema. Unknown fields and invalid unions are rejected. Common fields are operation ID, operation type, exact evidence quote plus start/end offsets into the immutable message revision, and a reason/uncertainty category. Quote offsets use a specified indexing convention (e.g. Unicode code points) and are validated against the stored revision; normalization is not proof. An optional model confidence is informational only until calibrated.

| Variant | Required fields and restrictions |
|---|---|
| `create` | Nonempty title, commitment category, optional typed scheduled-date expression and date-only deadline, optional candidate duplicate aliases. No task target. |
| `update_task` | One existing `T` alias and explicit field changes; specify `set` and `clear` separately so omission never clears a value. |
| `reschedule_task` | One `T` alias plus a typed date expression or explicit `later`. |
| `complete_task`, `cancel_task` | One `T` alias, no irrelevant date/title fields. |
| `revise_proposal` | One pending `P` alias and explicit permitted field changes. |
| `withdraw_proposal` | One pending `P` alias, no task fields. |

Clarification is a separate nullable `{question, operationIds[]}` object, not a `clarify` operation. It can refer to zero or more operation IDs. Dates are discriminated expressions (`none`, `relative_day`, `weekday`, `absolute`, `later`, `unresolved`) with only fields valid for that kind; schedule and deadline remain distinct. User-facing task titles and exact quotes have bounded lengths; validate dates and field limits server-side. The server resolves aliases from the recorded user-scoped context snapshot, validates target versions and refuses unknown, wrong-kind or unauthorized aliases. Proposal revision/withdrawal affects only pending suggestions; a committed task change requires a new reviewed task operation.

### Deduplication and dates

Transport retries use idempotency keys and unique mutation records, independent of semantic duplicate detection. Retrieve candidates from the current user's appropriate tasks and pending proposals using names and approximate similarity, optionally date as contextual information. A date match by itself is never sufficient; identical wording can describe a separate instance. Compare action, object, person, instance and qualifiers. If uncertain, show both with “keep existing,” “create another,” and a cancellation path. A model duplicate hint does not block a proposal. The same explicit commitment repeated in a conversation can be linked when supported and confirmed; ask if its identity is unclear. Re-run concurrency checks at apply without silently changing the user's choice.

Date resolution is a pure, table-tested function of the typed expression, original text, reference instant, user's IANA timezone, explicit calendar policy and any chosen planning-day rule. Store resolved date, resolver version and zone/anchor; retain source text only within retention rules. “Today,” “tomorrow” and weekdays must use explicitly documented semantics, including midnight, DST, year boundaries, weekday ambiguity and travel. If an absolute date is plausible but ambiguous, show options; do not guess a schedule from a deadline. Past dates are allowed or clarified depending on operation, not rejected wholesale. Until the timed-deadline model is separately approved, MVP task dates and deadlines are date-only; no implicit reminder delivery.

### Storage and consistency

The following are conceptual records, not a mandate for a particular ORM or number of tables:

- **User/settings:** owner ID, IANA timezone, approved language and retention settings, created time. Authentication records are handled by the chosen auth system.
- **Conversation and message revision:** owner, conversation ID, immutable revision ID/number, text, role, creation time and expiration. Record an explicit `supersedes_revision_id`; a separate message identity can point to its current revision. Capture reference instant and timezone for user turns. An assistant reply may contain sensitive user-derived text and follows the same retention.
- **Transcription:** owner, client upload ID, processing state, creation/expiry, optional link to the resulting message revision and temporary text. Assign an expiry at creation so abandoned uploads are purged; avoid keeping a second transcript after message creation. Processing claims have leases and recoverable failure states.
- **Analysis run and proposal:** owner, source message revision, run/version, status, alias-snapshot references, proposal ID and revision, operation, typed payload, state and minimal expiry-bound evidence. A retry is a new attempt within the same durable logical run or a new explicitly versioned run; only one active proposal set per message revision. `pending → applied/rejected/superseded/withdrawn/expired` is guarded, terminal transitions are not reversed. Record causation links for applied outcomes.
- **Task:** owner, title, status (`pending`, `completed`, `cancelled`), optional scheduled date and date-only deadline, version token and timestamps. An unscheduled task is Later. Link to applied proposal where retained, but task content remains after source deletion. Cancel versus delete must be explicit in UI.
- **Task event or mutation ledger:** minimal typed event, owner, task ID, operation, actor and time, plus content-free idempotency/provenance reference as needed. Avoid verbatim quotes or full before/after snapshots; if audit requirements require task values, define their retention explicitly. Hard delete task and events by default; any retained tombstone is content-free, has no live task FK, and requires an approved retention purpose.
- **Idempotency record:** owner + scoped key + canonical request hash, outcome/status and expiry. Persist mutation outcome atomically with its side effects. Keep responses minimal; do not cache transcripts or evidence beyond their deletion lifetime. Same key with a different request is a conflict. Applied proposal state is durable enough to prevent duplicate effects even after short-lived response caches expire.

Every owned relationship must enforce consistent ownership via composite constraints or transactionally checked references, as appropriate; all reads, writes, background jobs, exports and deletes independently authorize the owner. Use an explicit task version as a strong opaque ETag; increment on every meaningful change. Persist applied proposal state, task mutation, minimal event and idempotency result in one transaction. A schema migration must state foreign-key deletion behavior, indexes and constraints. Do not rely solely on an ORM query filter or expose a database internal token as a stable API contract.

### Public API semantics

Keep the original REST surface as a starting point, but freeze exact schemas before building clients. JSON uses camelCase, date-only values use ISO `YYYY-MM-DD`, and errors use Problem Details with stable codes. Every operation enforces ownership; cross-user resources return the same not-found behavior as absent resources. Cookie-based authentication, CSRF protection and session lifecycle depend on the approved deployment model.

| Operation | Contract requirements |
|---|---|
| Create message / transcribe | Authenticated, size/rate bounded, client-generated idempotency key plus request hash; return durable status and message revision ID. Transcription external calls may repeat after a crash unless the provider supports idempotency. A message is saved even if analysis fails. |
| Edit transcript/message | Require current revision via `If-Match`; return new revision and analysis status. Supersede prior pending proposals atomically, without changing applied tasks. A stale revision returns 412. |
| Retry analysis | Operate on the specified current revision and a stable logical run; never duplicate pending proposals or reapply committed changes. Return a conflict for superseded/deleted revisions. |
| Edit proposal | Require proposal revision and pending state; return new proposal revision. A stale proposal returns 412; a no-longer-pending state returns 409. |
| Apply/reject proposals | Require idempotency key, selected proposal IDs **with expected revisions**, and target task versions where applicable. Validate every selected and rejected ID before mutation. All-or-nothing: return committed outcomes for all items, or item-level conflicts with zero committed changes. A repeated same-key/same-body request returns its recorded result; key reuse with a different body returns 409. Reject overlap between selected and rejected lists. |
| Task change | Require task version on updates/lifecycle changes; stale `If-Match` returns 412, invalid state transition returns 409. Manual creates have their own idempotency key. |
| Conversation/account delete | Idempotent. Immediately prevent retrieval and invalidate in-flight commits; report completion or explicit pending deletion status according to the approved SLO. Deleted data must not be returned by a replay cache. |

**Proposed apply response:** `{ "applied": [{ "proposalId": "…", "taskId": "…", "operation": "create|update_task|reschedule_task|complete_task|cancel_task", "taskVersion": "…" }], "rejected": ["…"] }`. On conflict return a Problem Details object with item IDs and machine-readable reasons; do not return a mixed success response. The assistant's post-apply message is based on this response, not on model intent. Ensure apply and transcript edits racing on the same proposal have exactly one winning transaction. If the result response is lost, the same key retrieves its committed outcome, subject to deletion policy.

## 5. Privacy and retention specification

The following matrix is a **proposed invariant**, with exact periods and provider/backup guarantees open under D7. Deletion of a conversation preserves user-confirmed tasks, which can themselves contain information derived from the conversation; it removes source quotes and transcript-derived provenance. Users must be told this distinction and be able to delete tasks separately or delete the account.

| Data location | Creation and expiry | Conversation deletion / retention expiry | Account deletion and exceptions |
|---|---|---|---|
| Client audio (memory, IndexedDB or equivalent) | Optional recovery buffer with creation time and finite D7 TTL; clear after confirmed transcript persistence, explicit discard or expiry. Disclose shared-device/offline limits. | Delete accessible local copies on this device; a server cannot guarantee deletion from other or offline devices. Offer visible local discard and cleanup on next launch. | Attempt local cleanup on the active device; explain that other devices and browser backups are outside server control. |
| Provider audio, prompts and responses | Processors, regions, training and retention terms must be verified and disclosed before use; use minimal context. | Follow verified provider deletion and retention capabilities; do not promise immediate erasure where unavailable. Avoid undisclosed fallback providers. | Same; maintain processor inventory and applicable deletion requests. |
| `transcriptions` and abandoned uploads | Expire from creation even if never linked. Avoid duplicate transcript storage once message exists. | Delete linked transcription text and metadata containing user content; independently purge unlinked expired uploads. In-flight results cannot recreate deleted data. | Delete all owned rows and stored content. |
| Message revisions and assistant replies | Retain by the selected policy, with finite deadlines including edits and replies. | Delete all revisions and replies for the conversation; invalidate pending work and caches. | Delete all; protect against background-job resurrection. |
| Analysis runs and reports | Store model/prompt version, timings and content-free reason codes; avoid raw model output. Any retained output, alias snapshot, evidence or validation detail containing text inherits source expiry. | Delete/redact all derived text and source references; content-free aggregate metrics may remain only if non-identifying under the approved policy. | Delete user-linked run records or irreversibly aggregate under approved policy. |
| Pending proposals and evidence | Inherit source lifetime; unresolved drafts have finite TTL, warning and a visible expired state. `none` cannot mean indefinite retention. | Delete pending proposals and their payloads/quotes; invalidate all applies. Never convert expired proposals into tasks. | Delete all owned proposals and payloads. |
| Tasks and task evidence | User-confirmed tasks persist independently. Avoid storing source quotes separately; if evidence is stored temporarily, inherit source expiry. | Preserve task title and user-approved fields; remove all source quotes, source identifiers and derivatives that reproduce the source beyond task content. | Delete tasks and associated events. |
| Task events, idempotency records | Minimal operational metadata; no transcript, raw reply or source quote in JSON snapshots/cached responses. | Redact/delete source-derived content and invalidate replay responses that could reveal it; retain only safe mutation proof if needed. | Delete owned records subject to an explicitly approved legal/operational exception. |
| Logs, metrics, traces | No audio, transcript, task titles, prompt bodies or evidence. Scrub provider errors and headers. Set operational TTL. | Remove any user-linked records per approved policy; aggregate only when non-identifying. Test redaction. | Delete user-linked telemetry where technically and contractually supported. |
| Backups, exports and evaluation copies | Encrypt backups, restrict access, set expiry and document restore process. Exports are user-controlled copies; evaluation samples require separate informed consent and expiry. | Apply deletion tombstones after restore before serving traffic; backups age out on a documented SLO. Delete revocable evaluation copies; downloaded exports cannot be recalled. | Same; document any backup/processor delay and legal retention exception. |

Deletion/expiry must be idempotent and race-safe. Persist a deletion tombstone or generation before invalidating background work; recheck it in the transaction that would save a provider result. Define whether “don't keep” means purge immediately after an apply/reject decision or after a fixed short deadline; unresolved proposals cannot extend the deadline indefinitely. A scheduled cleanup has monitored execution, retries and a measurable completion SLO; no design assumes an idle API runs on schedule. Validate deletion by seeding unique canary strings into each store, deleting or expiring the conversation, scanning permitted live stores and verifying a restored backup respects tombstones.

## 6. Security baseline before private beta

Use proven authentication, secure HttpOnly cookies and CSRF/origin defenses where applicable; rotate sessions appropriately and rate-limit per user and network. Enforce ownership at every resource lookup and mutation, including alias resolution, retries, exports and deletion. Treat prompt content and model output as untrusted; a model cannot choose arbitrary IDs, call privileged tools, or bypass validation and confirmation. Limit audio duration, bytes and supported media by actual content; handle malformed files without persisting them indefinitely. Encrypt in transit and at rest, store secrets in a managed secret store, restrict database and provider access, set cost caps, and redact provider errors. Define incident response, backup access and retention; verify actual provider contractual and regional behavior before sending beta data. Run isolation, CSRF, injection, upload, abuse and deletion tests before onboarding.

## 8. Milestone 0 measurable acceptance criteria

### Dataset and protocol

1. Assemble at least **80 independently labeled text turns** in multi-turn contexts: at least 50 development turns and **30 held-out turns**, separated by conversation and author where practical. Held-out cases are not used in prompt examples, threshold tuning or model selection; if used to tune, replace them before the final gate. Each record includes a fixed instant, IANA timezone, current task/proposal state and version, expected operation(s), target, date, exact evidence and acceptable clarifications. Include consent and data provenance. No real personal content enters the set without permission.
2. Both sets contain Egyptian Arabic, mixed Arabic/English and English; the held-out set includes at least **10 Egyptian Arabic**, **10 code-switched**, and **5 English** turns (a turn can belong to more than one relevant slice; report overlap). Across the combined set include at least 10 no-task/venting or context-only turns, 10 negation/tentative/aspiration turns, 10 modifications with competing or ambiguous targets, and 10 correction cases, including corrections before and after apply. Include similar names and digits, multiple commitments, same-date unrelated tasks, repeated mentions, identical titles on distinct days, midnight, year boundary and DST-related cases. Report denominators for every slice; add examples if a category is too small to assess.
3. At least two qualified reviewers independently annotate the held-out expected operations and resolve disagreements before evaluation. Define one-to-one matching by operation type, action/object, correct target and date; ambiguous ground truth has documented acceptable alternatives. Use a human adjudicator for mismatches; an LLM judge may assist but is not the sole authority. Report confusion counts and exact binomial confidence intervals where applicable. Small samples limit precision; passing is a feasibility signal, not proof of production reliability.

### Text-model gate

4. On the frozen held-out set, **preselected definite-create precision ≥ 90%** and **definite-create recall ≥ 85%**, measured using the agreed one-to-one labels; show numerators and denominators. Also report false-task conversations and all omissions, including items omitted due to invalid schema/evidence. These are provisional feasibility thresholds, not approval for auto-apply.
5. Of all proposed modifications, **zero wrong-target proposals** on the held-out set; report the number of modifications and a 95% exact upper confidence bound. At least **90% of expected unambiguous modifications** have the correct type and target; ambiguous targets must result in clarification or abstention. This is a deliberately conservative small-sample gate; it does not establish a population wrong-target rate.
6. For explicitly resolvable date expressions, **≥ 95% exact date accuracy**, with numerator/denominator and separate results for midnight and code-switching. Where policy or user meaning is ambiguous, asking an appropriate question counts as correct; it must not be scored as a confident date. The expected midnight interpretation is finalized only after D2 approval.
7. Every proposed operation has valid exact source evidence in the correct revision and a valid target alias, and every schema-invalid response is surfaced as a failure or explicit retry—not a successful empty result. Deterministic contract tests cover unknown aliases, omitted versus cleared fields, invalid unions, negation and invalid evidence.
8. For the labeled duplicate cases, **zero distinct commitments are automatically suppressed** due to date, similarity or model hint; possible matches are visible and resolvable, including “create anyway.” Evaluate both false-merge and false-split counts. Request-retry tests prove no duplicate local mutation in the chosen test harness; external API calls are not claimed exactly once.
9. For labeled conversational cases, two reviewers independently assess at least **20 held-out replies** for relevance, language and non-pushy tone. At least **90%** are acceptable after adjudication; all explicit “do not organize” and pure-venting cases yield no task and no unwanted productivity prompt. No reply claims a task was saved prior to a confirmed persistence result. Evaluate correction turns with a state-transition fixture, including pending and previously applied outcomes; no silent reversal or create is acceptable.
10. Run the suite with one documented command or equivalent repeatable procedure; output anonymized case IDs, model and prompt versions, fixed inputs, timestamps, metric counts, slice results, latency and cost. Use a deterministic fixture mode for repeatable policy/schema tests and a separate live model run for quality. Do not include personal transcripts in general logs or the shared report.

**Gate decision:** Review results, confidence intervals, annotation disagreements, model/processor terms and failure examples with the user. If a threshold misses, document the causes, revise on development data, refresh held-out cases if compromised, and repeat; do not start Milestone 1 automatically. The text gate cannot establish microphone, STT, real-device, production security or provider-retention suitability.
